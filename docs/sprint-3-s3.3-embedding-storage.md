# S3.3 — Embedding Storage

## Objective

Define a reusable, versioned storage contract for the normalized retrieval embeddings generated by S3.2.

## Storage Contract

Each split is stored as a self-contained directory:

```text
embeddings/
└── stores/
    └── test/
        ├── embeddings.npy
        ├── metadata.json
        └── store.json
```

- `embeddings.npy`: float32 matrix with shape `[N, 128]`.
- `metadata.json`: ordered metadata records for dataset images.
- `store.json`: versioned storage manifest and integrity contract.

The critical alignment rule is:

```text
metadata_records[i] <-> embeddings[i]
```

Each metadata record contains:
- `image_path`
- `class`
- `description`

The dataset description is retained as metadata only and is not used as a class label.

## Design Decisions

1. NumPy is used for the embedding matrix because the project currently needs compact local storage and direct array access.
2. JSON is used for human-readable metadata and the storage manifest.
3. The embedding matrix and metadata remain separate so future retrieval can load embeddings without parsing metadata.
4. The store has an explicit `storage_version` for future format changes.
5. The storage layer validates dimensionality, finiteness, L2 normalization, row/metadata alignment, and required metadata fields.
6. The store does not implement similarity calculation, ranking, or Top-K retrieval. Those remain later Sprint 3/4 tasks.

## Runtime Validation

The S3.3 script reads the S3.2 `*.npy` and `*_generation.json` outputs, creates the versioned store, reloads it, and verifies that both embedding values and metadata survive the round trip unchanged.

Example:

```bash
python scripts/create_embedding_store.py --split test
```

Runtime artifacts under `embeddings/` remain ignored by Git.
